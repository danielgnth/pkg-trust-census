### Registry baseline (default toolchain, verified 2026-10-14)

| | Immutable versions | Install checks hash | Lockfile pins hashes | Client checks signature | Scoped, expiring tokens | No code at install |
|---|---|---|---|---|---|---|
| **PyPI** | ✓ yes (since 2026-07) | ✓ yes | ◐ partial | ✗ no | ◐ partial | ◐ partial |
| **npm** | ✓ yes | ✓ yes | ✓ yes | ✗ no | ✓ yes (since 2025-11) | ✓ yes (since 2026-07) |
| **crates.io** | ✓ yes | ✓ yes | ✓ yes | ✗ no | ✓ yes | ✗ no |
| **RubyGems** | ✓ yes | ✓ yes | ◐ partial | ✗ no | ✓ yes | ◐ partial |
| **Go** | ✓ yes | ✓ yes | ✓ yes | ✓ yes | – n/a | ✓ yes |
| **Maven Central** | ✓ yes | ◐ partial | ✗ no | ✗ no | ◐ partial | ◐ partial |
| **Packagist** | ✓ yes (since 2026-07) | ✗ no | ◐ partial | ✗ no | – n/a | ✓ yes |

What each column asks:

- **Immutable versions**: Once published, can a version's files never be replaced or added to?
- **Install checks hash**: Does the default client check each download against the registry's hash?
- **Lockfile pins hashes**: Does the default lockfile record artifact hashes, so later installs get identical bytes?
- **Client checks signature**: Does the default client check a signature or transparency log, so a compromised registry or mirror is detected?
- **Scoped, expiring tokens**: Can publish credentials be limited to specific packages and made to expire?
- **No code at install**: Does installing or building leave dependency code unexecuted by default?

Protections against tampering and bad releases, complementing the trust score, which measures whether
an outsider can verify who published a release and from what source. Not part of the score: these
describe ecosystem defaults, not the sampled packages. *since* marks a value that changed recently,
so the backfill quarters predate it.

#### Notes and sources

**Immutable versions**

- PyPI: yes. Filenames can never be reused; new files are rejected on releases older than 14 days (before: any release could gain new files). [1](https://pypi.org/help/#file-name-reuse "“PyPI does not allow for a filename to be reused, even once a project has been deleted and recreated.” (accessed 2026-10-14)") [2](https://blog.pypi.org/posts/2026-07-22-releases-now-reject-new-files-after-14-days/ "“The Python Package Index (PyPI) now rejects new files being uploaded to releases that are older than 14 days.” (accessed 2026-10-14)")
- npm: yes. A version number can never be reused, even after unpublishing. [1](https://docs.npmjs.com/policies/unpublish "“Once `package@version` has been used, you can never use it again. You must publish a new version even if you unpublished the old one.” (accessed 2026-10-14)")
- crates.io: yes. Versions are yanked, not replaced; deletion only within 72 h or for barely-used single-owner crates. [1](https://rust-lang.github.io/rfcs/3660-crates-io-crate-deletions.html "“The crate has been published for less than 72 hours” … “The crate has a single owner” (accessed 2026-10-14)")
- RubyGems: yes. A version cannot be pushed twice, even after it is yanked. [1](https://blog.rubygems.org/2015/04/13/permadelete-on-yank.html "“A gem version can not be published twice. So if you `gem yank` a version, you cannot quickly fix something then push a new version.” (accessed 2026-10-14)")
- Go: yes. The proxy and checksum database pin each version's contents; re-tagging upstream changes nothing. [1](https://go.dev/blog/supply-chain "“Since the Checksum Database guarantees that there can be only one source tree for a given module version, everyone using the proxy will see the same result as everyone bypassing it” (accessed 2026-10-14)")
- Maven Central: yes. Released components can never be changed or deleted. [1](https://central.sonatype.org/faq/can-i-change-a-component/ "“Once a component has been released and published to the Central Repository, it cannot be altered.” (accessed 2026-10-14)")
- Packagist: yes. Stable versions keep their original commit when the tag is moved upstream; dev branches stay mutable. Archives are still generated by the forge, so bytes may differ for the same commit. [1](https://blog.packagist.com/immutable-versions-on-packagist/ "“Stable version metadata on Packagist.org is now immutable. Once a version has been published, the git reference it points to can no longer change.” … “Dev versions, which track branches, are unaffected.” (accessed 2026-10-14)") [2](https://blog.packagist.com/an-update-on-composer-packagist-supply-chain-security/ "“Packagist.org hosting immutable build artifacts directly, with SLSA build provenance and Sigstore attestations verified on the Composer client side.” (accessed 2026-10-14)")

**Install checks hash**

- PyPI: yes. pip checks each file against the sha256 the index lists for it, without needing --require-hashes. [1](https://github.com/pypa/pip/blob/main/src/pip/_internal/operations/prepare.py "“if not self.require_hashes: return req.hashes(trust_internet=True)” (accessed 2026-10-14)")
- npm: yes. Tarballs are checked against dist.integrity. [1](https://docs.npmjs.com/cli/configuring-npm/package-lock-json "“integrity: A `sha512` or `sha1` Standard Subresource Integrity string for the artifact that was unpacked in this location.” (accessed 2026-10-14)")
- crates.io: yes. Cargo checks every .crate against the index's sha256 (cksum). [1](https://doc.rust-lang.org/cargo/reference/registry-index.html "“A SHA256 checksum of the `.crate` file.” (accessed 2026-10-14)") [2](https://github.com/rust-lang/cargo/blob/master/src/sources/registry/download.rs "“anyhow::bail!('failed to verify the checksum of `{}`', pkg)” (accessed 2026-10-14)")
- RubyGems: yes. Bundler validates gems against the compact index's checksums. [1](https://github.com/ruby/rubygems/blob/master/lib/bundler/endpoint_specification.rb "“@checksum = Checksum.from_api(checksum, @spec_fetcher.uri)” (accessed 2026-10-14)") [2](https://github.com/ruby/rubygems/blob/master/lib/bundler/checksum.rb "“raise(ChecksumMismatchError.new(display_name, existing, checksum))” (accessed 2026-10-14)")
- Go: yes. Every module is checked against go.sum and the checksum database. [1](https://go.dev/ref/mod#checksum-database "“the go command may connect to the checksum database to verify cryptographic hashes of modules not listed in go.sum” (accessed 2026-10-14)")
- Maven Central: partial. Maven 3 checks .sha1 files but only warns on mismatch by default; Maven 4 fails. The checksums come from the same server as the artifact. [1](https://maven.apache.org/resolver/about-checksums.html "“Checksums retrieved alongside an artifact or over the same transport only provide integrity verification.” (accessed 2026-10-14)") [2](https://issues.apache.org/jira/browse/MNG-5728 "“The default checksum policy when obtaining artifacts during a build is currently, by default, 'warn'.” … “Fix Version/s: 4.0.0-alpha-2” (accessed 2026-10-14)")
- Packagist: no. Packagist publishes an empty dist.shasum for forge-hosted archives, so Composer has nothing to check; the commit in the archive URL is the only pin. [1](https://repo.packagist.org/p2/monolog/monolog.json "“'shasum': ''” (accessed 2026-10-14)")

**Lockfile pins hashes**

- PyPI: partial. pip has no default lockfile; PEP 751 pylock.toml (2025) and tools like uv and Poetry record hashes. [1](https://peps.python.org/pep-0751/ "“Considering there are at least five well-known solutions to this problem in the community (PDM, `pip freeze`, pip-tools, Poetry, and uv)” … “A lock file MUST be named `pylock.toml`” (accessed 2026-10-14)")
- npm: yes. package-lock.json records each package's integrity hash. [1](https://docs.npmjs.com/cli/configuring-npm/package-lock-json "“integrity: A `sha512` or `sha1` Standard Subresource Integrity string for the artifact that was unpacked in this location.” (accessed 2026-10-14)")
- crates.io: yes. Cargo.lock records each crate's checksum. [1](https://github.com/rust-lang/rustlings/blob/main/Cargo.lock "“checksum = '” (accessed 2026-10-14)")
- RubyGems: partial. Gemfile.lock CHECKSUMS since Bundler 2.6, opt-in (bundle lock --add-checksums). [1](https://blog.rubygems.org/2024/12/19/bundler-v2-6 "“For a single lockfile, you can run `bundle lock --add-checksums`. This will add a new `CHECKSUMS` section to the lockfile” (accessed 2026-10-14)")
- Go: yes. go.sum records each module's hash. [1](https://go.dev/blog/supply-chain "“It contains a list of cryptographic hashes of each dependency that contributes to the build.” (accessed 2026-10-14)")
- Maven Central: no. Maven has no lockfile; third-party plugins exist. [1](https://github.com/chains-project/maven-lockfile "“generating a lock file that contains the checksums of all the artifacts and dependencies” (accessed 2026-10-14)")
- Packagist: partial. composer.lock pins the commit, but the archive hash is empty for forge-hosted packages. [1](https://getcomposer.org/doc/01-basic-usage.md#commit-your-composer-lock-file-to-version-control "“writes all of the packages and their exact versions to the `composer.lock` file” (accessed 2026-10-14)") [2](https://repo.packagist.org/p2/monolog/monolog.json "“'shasum': ''” (accessed 2026-10-14)")

**Client checks signature**

- PyPI: no. PEP 458 (TUF-signed index) is not deployed; PEP 740 attestations are not verified by pip. [1](https://peps.python.org/pep-0458/ "“should be integrated with the Python Package Index” (accessed 2026-10-14)")
- npm: no. Registry signatures are checked only by an explicit `npm audit signatures`. [1](https://docs.npmjs.com/verifying-registry-signatures "“Registry signatures can be verified using the following `audit` command:” (accessed 2026-10-14)")
- crates.io: no. The index is not signed; TUF signing is an open Rust project goal. [1](https://rust-lang.github.io/goals/2025h1/verification-and-mirroring.html "“We would like to have a experimental out-of-band version of a signing pipeline for the project for releases and crates.io.” (accessed 2026-10-14)")
- RubyGems: no. Signed-gem verification is opt-in (gem install -P MediumSecurity); signing is rarely used. [1](https://guides.rubygems.org/security/ "“users opt into verification with a trust policy, using `gem install -P MediumSecurity`” … “In practice signing is rarely used” (accessed 2026-10-14)")
- Go: yes. The go command checks every module against the signed sum.golang.org log by default. [1](https://go.dev/ref/mod#checksum-database "“The default value of `GOSUMDB` is `sum.golang.org`, the public checksum database operated by Google” (accessed 2026-10-14)")
- Maven Central: no. Maven does not check PGP signatures; a plugin is needed. [1](https://www.simplify4u.org/pgpverify-maven-plugin/ "“This plugin allows you to automatically verify PGP signature of all project dependencies.” (accessed 2026-10-14)")
- Packagist: no. There is nothing signed to check. [1](https://blog.packagist.com/an-update-on-composer-packagist-supply-chain-security/ "“Packagist.org hosting immutable build artifacts directly, with SLSA build provenance and Sigstore attestations verified on the Composer client side.” (accessed 2026-10-14)")

**Scoped, expiring tokens**

- PyPI: partial. API tokens can be scoped to one project but never expire (trusted publishing tokens do). [1](https://pypi.org/help/#apitoken "“Alternatively, you can limit a token's scope to a specific project.” (accessed 2026-10-14)")
- npm: yes. Granular tokens only; write tokens expire after at most 90 days, classic tokens were revoked. [1](https://github.blog/changelog/2025-11-05-npm-security-update-classic-token-creation-disabled-and-granular-token-changes/ "“New npm classic tokens can no longer be created” … “All npm existing granular tokens with write permissions are now capped at 90-day maximum lifetime” (accessed 2026-10-14)")
- crates.io: yes. Tokens can be scoped by endpoint and crate, with an optional expiry. [1](https://blog.rust-lang.org/2023/06/23/improved-api-tokens-for-crates-io/ "“our 'New API Token' page now supports endpoint scopes, crate scopes and expiration dates” (accessed 2026-10-14)")
- RubyGems: yes. API keys have per-action and per-gem scopes, with an optional expiry. [1](https://guides.rubygems.org/api-key-scopes/ "“will allow you to scope one of your gems to the API key” … “You can also optionally set an expiration date for the key.” (accessed 2026-10-14)")
- Go: n/a. No publish credentials exist. [1](https://go.dev/blog/supply-chain "“In Go, there is no such thing as a package repository account.” (accessed 2026-10-14)")
- Maven Central: partial. User tokens can be given an expiry; no per-namespace scoping is documented. [1](https://central.sonatype.org/publish/generate-portal-token/ "“Specify a display name and an expiration for the token” (accessed 2026-10-14)")
- Packagist: n/a. Nothing is uploaded; tokens only trigger re-indexing. [1](https://packagist.org/about "“New versions of your package are automatically fetched from tags you create in your VCS repository.” (accessed 2026-10-14)")

**No code at install**

- PyPI: partial. Wheels run no code; source distributions run their build backend. [1](https://pip.pypa.io/en/stable/topics/secure-installs/ "“By default, pip does not perform any checks to protect against remote tampering and involves running arbitrary code from distributions.” … “Disallow source distributions, by passing `--only-binary :all:`” (accessed 2026-10-14)")
- npm: yes. npm 12 runs no dependency install scripts unless allowed (before: all ran). [1](https://github.com/orgs/community/discussions/198547 "“Every `npm install` runs scripts from every transitive dependency” … “Making script execution opt-in closes that path” (accessed 2026-10-14)")
- crates.io: no. Dependencies' build scripts and procedural macros run at build time. [1](https://doc.rust-lang.org/cargo/reference/build-scripts.html "“Just before a package is built, Cargo will compile a build script into an executable (if it has not already been built). It will then run the script” (accessed 2026-10-14)")
- RubyGems: partial. Pure-Ruby gems run nothing; native extensions run extconf.rb on install. [1](https://guides.rubygems.org/gems-with-extensions/ "“Creating a gem that includes an extension that is built at install time.” (accessed 2026-10-14)")
- Go: yes. An explicit design goal: neither fetching nor building runs dependency code. [1](https://go.dev/blog/supply-chain "“It is an explicit security design goal of the Go toolchain that neither fetching nor building code will let that code execute, even if it is untrusted and malicious.” (accessed 2026-10-14)")
- Maven Central: partial. Dependency jars are not run, but javac ran classpath annotation processors implicitly until JDK 23; build plugins run by the project's choice. [1](https://inside.java/2024/06/18/quality-heads-up/ "“starting with JDK 23, javac requires an additional command-line option to enable annotation processing.” (accessed 2026-10-14)")
- Packagist: yes. Only the root project's scripts run; dependency plugins need explicit allow-plugins (Composer 2.2+). [1](https://getcomposer.org/doc/articles/scripts.md "“Only scripts defined in the root package's `composer.json` are executed.” (accessed 2026-10-14)") [2](https://getcomposer.org/doc/06-config.md#allow-plugins "“As of Composer 2.2.0, the `allow-plugins` option adds a layer of security allowing you to restrict which Composer plugins are able to execute code during a Composer run.” (accessed 2026-10-14)")
