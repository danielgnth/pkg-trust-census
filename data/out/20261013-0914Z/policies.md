### Registry governance and containment (verified 2026-10-14)

| | Owned namespaces | Confusable names blocked | Uploads scanned | Withdraw, keep lockfiles | Deletion restricted | Client acts on advisories |
|---|---|---|---|---|---|---|
| **PyPI** | ✗ no | ◐ partial | ◐ partial | ✓ yes | ✗ no | ✗ no |
| **npm** | ◐ partial | ◐ partial | ◐ partial | ◐ partial | ✓ yes | ◐ partial |
| **crates.io** | ✗ no | ◐ partial | ◐ partial | ✓ yes | ✓ yes | ✗ no |
| **RubyGems** | ✗ no | ◐ partial | ✓ yes | ✗ no | ✗ no | ✗ no |
| **Go** | ✓ yes | – n/a | ✗ no | ✓ yes | ✓ yes | ✗ no |
| **Maven Central** | ✓ yes | – n/a | ✗ no | ✗ no | ✓ yes | ✗ no |
| **Packagist** | ✓ yes | ◐ partial | ✓ yes (since 2026-03) | ◐ partial (since 2026-07) | ◐ partial (since 2026-07) | ✓ yes |

What each column asks:

- **Owned namespaces** (governance): Can a publisher own a name prefix that nobody else can publish into?
- **Confusable names blocked** (governance): Does registration reject a name confusable with an existing package?
- **Uploads scanned** (governance): Are new uploads analysed for malware automatically, by the registry or a feed it acts on?
- **Withdraw, keep lockfiles** (containment): Can a version be withdrawn from new resolution while existing lockfiles still install it (yank)?
- **Deletion restricted** (containment): Are authors prevented from deleting a published version after the fact?
- **Client acts on advisories** (containment): Does the default client warn about or block known-vulnerable versions without extra tools?

#### Notes and sources

**Owned namespaces**

- PyPI: no. One flat namespace. Namespace prefixes (PEP 752) are accepted but not deployed. [1](https://peps.python.org/pep-0752/ "“Status: Accepted” … “The current ecosystem lacks a way for projects with many packages to signal a verified pattern of ownership” (accessed 2026-10-14)")
- npm: partial. @scope/ names belong to a user or organisation, but scopes are optional and unscoped names are first come, first served. [1](https://docs.npmjs.com/about-scopes "“When you sign up for an npm user account or create an organization, you are granted a scope that matches your user or organization name.” (accessed 2026-10-14)")
- crates.io: no. One flat namespace. Namespaced crates (RFC 3243) are accepted but not implemented on crates.io. [1](https://rust-lang.github.io/goals/2026/open-namespaces.html "“Navigate the cross-team design work to get RFC #3243 implemented.” (accessed 2026-10-14)")
- RubyGems: no. One flat namespace; prefixes are a naming convention only. [1](https://guides.rubygems.org/name-your-gem/ "“If you're adding functionality to another gem, use a dash.” (accessed 2026-10-14)")
- Go: yes. The module path is a domain or repository path, so whoever controls the domain or repository controls the name. [1](https://go.dev/ref/mod#module-path "“The repository root path is the portion of the module path that corresponds to the root directory of the version control repository where the module is developed.” (accessed 2026-10-14)")
- Maven Central: yes. A groupId must be verified before publishing: a DNS TXT record for the domain, or the code-hosting account for io.github.*. [1](https://central.sonatype.org/register/namespace/ "“You can prove domain ownership by adding a DNS TXT record with a value set to the Verification Key we assigned to your namespace request.” … “Sonatype can, in most cases, automatically verify and provision publishing access to a namespace that looks like io.github.<your GitHub username>” (accessed 2026-10-14)")
- Packagist: yes. A vendor prefix belongs to the first account to publish under it; nobody else can add packages to it. [1](https://blog.packagist.com/preventing-dependency-hijacking/ "“Packagist.org reserves vendor name prefixes for the maintainer as soon as they publish a first package. Nobody else can then publish another package with the my-company/ vendor prefix without a maintainer's consent.” (accessed 2026-10-14)")

**Confusable names blocked**

- PyPI: partial. A new name is rejected if it matches any existing project after removing . _ - and folding l/i→1 and o→0 (ultranormalize). Other misspellings pass. [1](https://github.com/pypi/warehouse/blob/main/warehouse/migrations/versions/d18d443f89f0_ultranormalize_name_function.py "“regexp_replace($1, '(\.|_|-)', '', 'ig'), '(l|L|i|I)', '1', 'ig' ), '(o|O)', '0', 'ig'” (accessed 2026-10-14)") [2](https://github.com/pypi/warehouse/blob/main/warehouse/packaging/services.py "“func.ultranormalize_name(Project.name) == func.ultranormalize_name(name) ) ).first(): raise ProjectNameUnavailableSimilarError(similar_project_name)” (accessed 2026-10-14)")
- npm: partial. A new name is rejected if it equals an existing one once punctuation is removed (2017). Other misspellings pass. [1](https://blog.npmjs.org/post/168978377570/new-package-moniker-rules "“we remove punctuation from its name and compare it to existing package names. If the names are identical without punctuation, we do not allow the package to be created.” (accessed 2026-10-14)")
- crates.io: partial. - and _ are equivalent (canon_crate_name), so such variants cannot be registered. A typosquat check runs after publication and only emails the crates.io team. [1](https://github.com/rust-lang/crates.io/blob/main/migrations/20150319224700_dumped_migration_93/up.sql "“SELECT replace(lower($1), '-', '_')” (accessed 2026-10-14)") [2](https://github.com/rust-lang/crates.io/blob/main/migrations/20150319224701_dumped_migration_94/up.sql "“CREATE UNIQUE INDEX index_crates_name ON crates (canon_crate_name(name));” (accessed 2026-10-14)") [3](https://github.com/rust-lang/crates.io/blob/main/src/worker/jobs/typosquat.rs "“Checking new crate for potential typosquatting” (accessed 2026-10-14)")
- RubyGems: partial. A push is rejected if the name equals an established gem's (≥ 10,000 downloads or released in the last five years) ignoring case, _ and -. [1](https://github.com/rubygems/rubygems.org/blob/master/app/models/gem_typo.rb "“DOWNLOADS_THRESHOLD = 10_000 LAST_RELEASE_TIME = 5.years.ago” … “regexp_replace(upper(name), '[_-]', '', 'g') = regexp_replace(upper(?), '[_-]', '', 'g')” (accessed 2026-10-14)")
- Go: n/a. Names are domains and repository paths; there is no registration step. [1](https://go.dev/ref/mod#module-path "“A module path should describe both what the module does and where to find it.” (accessed 2026-10-14)")
- Maven Central: n/a. Names sit under a verified namespace, so confusable names fall under namespace verification. [1](https://central.sonatype.org/register/namespace/ "“Before Sonatype can grant you permissions to publish under your requested namespace, we must validate that you own the web domain reflected by your namespace.” (accessed 2026-10-14)")
- Packagist: partial. A package whose vendor is one edit away from an existing vendor with the same package name is rejected if the existing package has ≥ 1M downloads; otherwise the admins are emailed. [1](https://github.com/composer/packagist/blob/main/src/Validator/TypoSquattersValidator.php "“if (levenshtein($existingVendor, $value->getVendor()) <= 1) {” … “if ($this->downloadManager->getTotalDownloads($existingPackage['id']) >= 1_000_000) {” (accessed 2026-10-14)")

**Uploads scanned**

- PyPI: partial. Report-driven: trusted researchers (Observers) report through an API, and admins quarantine projects (hidden from the index, frozen) pending review. Auto-quarantine is proposed. [1](https://blog.pypi.org/posts/2024-12-30-quarantine/ "“I had previously built a new beta API infrastructure to allow Observers to report malicious Projects.” … “Project is not installable (hidden from simple index) while in quarantine - Project is not modifiable by the project owner while in quarantine” (accessed 2026-10-14)")
- npm: partial. Malicious packages are removed and replaced by a '0.0.1-security' holding package, but npm does not document how they are detected. [1](https://registry.npmjs.org/wesily "“'description': 'security holding package'” (accessed 2026-10-14)")
- crates.io: partial. Typosquat checks on new crates alert the team; malicious crates are deleted, their accounts disabled and a RustSec advisory published. [1](https://github.com/rust-lang/crates.io/blob/main/src/worker/jobs/typosquat.rs "“Checking new crate for potential typosquatting” (accessed 2026-10-14)") [2](https://blog.rust-lang.org/2026/02/13/crates.io-malicious-crate-update "“In all cases, the crates were deleted, the user accounts that published them were immediately disabled” … “We will always publish a RustSec advisory when a crate is removed for containing malware.” (accessed 2026-10-14)")
- RubyGems: yes. Every upload gets static and dynamic analysis and a risk score; high scores go to manual review. The team reports finding 70–80% of the malware it removes itself. [1](https://blog.rubygems.org/2025/08/25/rubygems-security-response.html "“Every gem upload is analyzed using both static and dynamic code analysis, including behavioral checks and metadata review.” … “Higher-risk gems are escalated for manual review by a member of our security team.” … “our team detects the majority (roughly 70-80%) of malicious packages before they are ever reported to us or the public.” (accessed 2026-10-14)")
- Go: no. The mirror caches whatever a VCS serves; malicious modules are removed on request. [1](https://proxy.golang.org/ "“the mirror aims to cache content in order to avoid breaking builds for people that depend on your package, so this bad release may still be available in the mirror even if it is not available at the origin.” (accessed 2026-10-14)")
- Maven Central: no. Central validates signatures and metadata on upload but documents no malware analysis; malicious components are removed once reported. [1](https://www.sonatype.com/blog/malware-removed-from-maven-central "“Upon becoming aware of the issue, we immediately blocked access to those components removed them from the Central Repository” (accessed 2026-10-14)")
- Packagist: yes (since 2026-03). Aikido's malware detections are imported and shipped in the metadata Composer reads; Composer 2.10 blocks flagged versions. [1](https://blog.packagist.com/an-update-on-composer-packagist-supply-chain-security/ "“In March 2026, Packagist.org started importing malware detection results from Aikido” … “Composer 2.10, introducing a unified dependency policy framework that covers malware-flagged versions” (accessed 2026-10-14)")

**Withdraw, keep lockfiles**

- PyPI: yes. Yank (PEP 592): resolvers skip the release unless it is pinned exactly. [1](https://peps.python.org/pep-0592/ "“Yanking a file allows authors to effectively delete a file, without breaking things for people who have pinned to exactly a specific version.” (accessed 2026-10-14)")
- npm: partial. npm deprecate only warns; the version still resolves. Hiding it means unpublishing, which also breaks lockfiles. [1](https://docs.npmjs.com/deprecating-and-undeprecating-packages-or-package-versions "“unpublishing removes a package from the registry entirely, meaning anyone who relied on it will no longer be able to use it, with no warning.” (accessed 2026-10-14)")
- crates.io: yes. cargo yank: new resolution skips the version; Cargo.lock keeps using it. [1](https://doc.rust-lang.org/cargo/commands/cargo-yank.html "“Yanking only prevents Cargo from selecting this version when resolving dependencies by default. Existing lock files or direct downloads are not affected” (accessed 2026-10-14)")
- RubyGems: no. A yank removes the .gem file, so locked installs of it fail. [1](https://blog.rubygems.org/2015/04/13/permadelete-on-yank.html "“`gem yank` will remove the .gem file from S3 and our CDN” (accessed 2026-10-14)")
- Go: yes. A retract directive in a later go.mod hides the version from new resolution; go.mod requirements keep it. [1](https://go.dev/ref/mod#go-mod-file-retract "“When a module version is retracted, users will not upgrade to it automatically using go get, go mod tidy, or other commands. Builds that depend on retracted versions should continue to work” (accessed 2026-10-14)")
- Maven Central: no. Nothing can be withdrawn. [1](https://central.sonatype.org/faq/can-i-change-a-component/ "“Once a component has been released and published to the Central Repository, it cannot be altered.” (accessed 2026-10-14)")
- Packagist: partial (since 2026-07). Soft deletion removes a version from the metadata Composer resolves, keeps a record and can be undone; lockfiles fetch archives from the forge, which the maintainer controls. [1](https://blog.packagist.com/immutable-versions-on-packagist/ "“Soft-deleted versions are removed from the metadata Composer reads, so Composer can no longer resolve a version that has been pulled, regardless of the reason.” … “Where recovery makes sense, the version shows a Recover button.” (accessed 2026-10-14)")

**Deletion restricted**

- PyPI: no. Owners can delete files and releases at any time; only the filename can never be reused. [1](https://pypi.org/help/#file-name-reuse "“Deletion of a project, release or file on PyPI is permanent and irreversible, without exception.” (accessed 2026-10-14)")
- npm: yes. Unpublishing is allowed within 72 hours, or later only for packages with no dependents, under 300 weekly downloads and one owner. [1](https://docs.npmjs.com/policies/unpublish "“you can unpublish anytime within the first 72 hours after publishing.” … “no other packages in the npm Public Registry depend on it - it had less than 300 downloads over the last week - it has a single owner/maintainer” (accessed 2026-10-14)")
- crates.io: yes. Deletion is allowed within 72 hours, or later only for crates with one owner, no dependents and few downloads (RFC 3660). [1](https://rust-lang.github.io/rfcs/3660-crates-io-crate-deletions.html "“The crate has been published for less than 72 hours” … “The crate has been downloaded less than 100 times for each month it has been published.” (accessed 2026-10-14)")
- RubyGems: no. A yank, possible at any time, deletes the file; only the version number stays taken. [1](https://blog.rubygems.org/2015/04/13/permadelete-on-yank.html "“`gem yank` will remove the .gem file from S3 and our CDN” … “A gem version can not be published twice.” (accessed 2026-10-14)")
- Go: yes. The mirror and checksum database keep every version; deleting the tag upstream changes nothing. [1](https://proxy.golang.org/ "“The same situation applies if you delete your entire repository.” (accessed 2026-10-14)")
- Maven Central: yes. Released components can never be changed or deleted. [1](https://central.sonatype.org/faq/can-i-change-a-component/ "“However you will be unable to change the contents of something that has been pushed to the Central Repository already.” (accessed 2026-10-14)")
- Packagist: partial (since 2026-07). Deletion is now a recoverable soft delete with a public record, but the code lives in the maintainer's repository, which they can delete. [1](https://blog.packagist.com/immutable-versions-on-packagist/ "“soft-deletions, recoveries, and blocked reference changes all leave a permanent public entry” (accessed 2026-10-14)") [2](https://packagist.org/about "“New versions of your package are automatically fetched from tags you create in your VCS repository.” (accessed 2026-10-14)")

**Client acts on advisories**

- PyPI: no. pip does not check advisories; pip-audit is separate. [1](https://pypi.org/project/pip-audit/ "“pip-audit is a tool for scanning Python environments for packages with known vulnerabilities.” (accessed 2026-10-14)")
- npm: partial. npm install runs an audit by default and reports known vulnerabilities, but installs them. [1](https://docs.npmjs.com/cli/v11/commands/npm-install#audit "“Default: true - Type: Boolean When 'true' submit audit reports alongside the current npm command” (accessed 2026-10-14)")
- crates.io: no. Cargo does not check advisories; cargo-audit (RustSec) is separate. [1](https://rustsec.org/ "“cargo audit Scanning Cargo.lock for vulnerabilities” (accessed 2026-10-14)")
- RubyGems: no. Bundler does not check advisories; bundler-audit is separate. [1](https://github.com/rubysec/bundler-audit "“Checks for vulnerable versions of gems in `Gemfile.lock`.” (accessed 2026-10-14)")
- Go: no. The go command does not check advisories; govulncheck is separate. [1](https://go.dev/doc/security/vuln/ "“Vulnerability checking is integrated into Go's tools and services, including a new command line tool, govulncheck” (accessed 2026-10-14)")
- Maven Central: no. Maven does not check advisories; plugins such as OWASP Dependency-Check are separate. [1](https://owasp.org/www-project-dependency-check/ "“Dependency-Check is a Software Composition Analysis (SCA) tool suite that identifies project dependencies and checks if there are any known, publicly disclosed, vulnerabilities.” (accessed 2026-10-14)")
- Packagist: yes. Composer blocks versions with security advisories during update/require by default (policy.advisories.block); installs from a lockfile are not checked. [1](https://getcomposer.org/doc/06-config.md#policy "“Defaults to `true`. When `true`, package versions with active security advisories are blocked and cannot be installed during `update`/`require`/`remove`” (accessed 2026-10-14)")
